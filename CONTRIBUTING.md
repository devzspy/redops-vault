# Contributing to RedOps Vault

Issues and pull requests are welcome. This document covers what makes a
contribution easy to review and merge.

## Before you start

Bug fixes and small, self-contained features are fine to send straight as
a PR. For anything bigger — a change to the data model, a new domain
(a new kind of record alongside findings/loot/credentials/etc.), or a
change to how an existing feature behaves — open an issue first. A quick
conversation up front is cheaper than a large PR that has to be reworked
or that duplicates something already in progress.

## Development setup

See the [README](README.md) for running the app (Docker Compose or a
local venv + Postgres) and the [Running tests](README.md#running-tests)
section for the test suite, which runs against a temporary SQLite database
and needs nothing else installed.

```bash
pip install -r requirements.txt
pytest
```

CI runs the same `pytest` suite on every PR (see
[`.github/workflows/tests.yml`](.github/workflows/tests.yml)) — a PR that
doesn't pass it won't be merged.

## Architecture: every feature has four surfaces

This is the one convention that isn't obvious from looking at a single
file, so read it before writing code (or prompting an AI assistant to
write it — see below).

Every operator-facing feature in RedOps Vault is implemented four times,
kept deliberately in sync:

| Surface | Where |
|---|---|
| Web UI | `app/blueprints/<domain>/` |
| JSON API | `app/blueprints/api/<domain>.py` |
| MCP server (AI agent tools) | `mcp_server/tools/<domain>.py` |
| Operator CLI | `cli/commands/<domain>.py` |

The web UI calls into the models/services directly; the API is the one
JSON contract that the MCP server and the CLI both wrap. If you add a new
domain, or a new field/action to an existing one, wire it through all four
— not just whichever one you happened to be looking at. `app/blueprints/api/serializers.py`
has one `*_dict()` function per model, reused by every JSON-producing
route, so API output and HTML output can't drift apart; the MCP tool and
CLI command docstrings/help text should describe the same fields.

**Admin (user management) and Backups are the one deliberate exception** —
those stay web UI-only, on purpose, everywhere in the codebase.

If you're not sure whether your change needs all four surfaces touched,
say so in the PR description and it'll get sorted out in review.

## Tests

New behavior needs a regression test in `tests/`. Look at the existing
test file for the domain you're touching (e.g. `tests/test_targets.py`,
`tests/test_api_targets.py`) for the fixtures and conventions already in
use — most tests drive the app through `admin_client`/`api_client`
fixtures rather than calling service functions directly, so the test
exercises the same path a real request would.

## Contributing with AI assistance

Using Claude, Copilot, ChatGPT, or similar tools to help write a
contribution is fine — a large share of this codebase itself was written
that way. A few rules make that work for everyone instead of turning into
review burden:

- **You are the author.** Submitting a PR means you've read every line of
  the diff, understand why it's correct, and can answer follow-up
  questions about it. "I'm not sure, the AI wrote that part" is not an
  acceptable answer to a review comment.
- **Verify, don't just generate.** Actually run `pytest` locally and
  actually exercise the feature (web UI, API call, MCP tool call —
  whatever's relevant) before claiming it works. A PR description that
  asserts something was tested should mean it was tested by a human
  running it, not inferred by a model.
- **Watch for hallucination.** Fabricated function/route names, imaginary
  config options, invented CVEs or library behavior, and confidently wrong
  claims about what existing code does are the most common failure mode
  of AI-assisted changes. Cross-check anything the AI asserts about this
  codebase against the actual source.
- **Follow the architecture above.** An AI assistant working from a narrow
  prompt will often implement only the web UI and miss the API/MCP/CLI
  surfaces, because it never saw that this project keeps them in sync.
  Point it at this file, or wire the other surfaces yourself.
- **Disclose substantial AI authorship** in the PR description (a line
  like "written with Claude/Copilot assistance" is enough). This isn't
  about credit — it helps reviewers calibrate how much to double-check,
  the same way you'd mention a change was auto-generated by a codemod.
- **Low-effort/mass-produced PRs will be closed without detailed review.**
  A PR that's clearly a model's unreviewed first draft — unrelated diff
  noise, no evidence of local testing, generic or templated description
  that doesn't reflect what actually changed — wastes more reviewer time
  than it saves and will be closed. This applies regardless of whether AI
  was involved; it just tends to be how AI-generated spam shows up in
  practice.

## Commits and licensing

By submitting a pull request, you agree your contribution is licensed
under this repository's [Apache License 2.0](LICENSE) and that you have
the right to submit it under that license (this matters as much for
AI-assisted code as for hand-written code — you're still the one
attesting to it). A `Signed-off-by` trailer on your commits
(`git commit -s`) recording that is appreciated but not currently
enforced by CI.

## Reporting security issues

Don't open a public issue for a security vulnerability. See
[SECURITY.md](SECURITY.md).
